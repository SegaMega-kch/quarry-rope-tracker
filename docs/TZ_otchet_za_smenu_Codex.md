# ТЗ: вкладка «Отчёт за смену» для rapmas.ru

Версия: 1.0. Дата: 29.09.2026.

**Статус: живое ТЗ по согласованным результатам интервью.** Определены ввод, справочники, смены, предварительные и итоговые отчёты, история, исправления и правила подготовки данных для аналитики. Позднейшие уточнения по мобильной фотографии и итоговой картинке MAX приведены в разделах 17 и 20 и имеют приоритет над ранними отложенными формулировками.

В документе разделены:

- **Согласованные требования** — решения пользователя в интервью.
- **Технические предложения** — способ сохранить эти требования при реализации; Codex должен сверить их с исходным кодом проекта.
- **Открытые решения** — перечислены в разделе 12. Их нельзя заполнять догадками.

## 1. Назначение и приоритет

Добавить на существующий сайт rapmas.ru вкладку «Отчёт за смену». Мастер переносит показатели работы экскаваторов из доступной ему производственной системы, сохраняет отчёт и отправляет его через бота MAX.

Главный критерий — простота. Основное устройство — компьютер. Нужна понятная таблица, удобный ввод с клавиатуры и минимум действий. Редкие операции не должны усложнять обычное заполнение.

Пользователь сначала просит составить ТЗ для Codex. Исходный код, действующая архитектура rapmas.ru и код бота в рамках интервью не исследованы. Не считать макет описанием существующей реализации сайта.

## 2. Изоляция данных и пользователи

### Согласовано

1. Для блока нужна **отдельная база данных**, не смешанная с другими базами и бизнес-данными сайта. Это самостоятельный учёт нарядов.
2. Данные накапливаются; пользователь должен иметь доступ к прошлым отчётам и возможность дальнейшей аналитики.
3. У мастеров четырёх смен один общий набор экскаваторов. Мастера по очереди принимают ту же технику. За свою смену отчёт заполняет один мастер.
4. Мастера, как и пользователь, могут редактировать справочники экскаваторов, нормативов и причин невыполнения.
5. Любой мастер может открыть прошлый отчёт через «Историю» и исправить его. Прежние версии, автор, время и состав изменений сохраняются.

### Технические предложения

- Реализацию отдельной БД определить после изучения проекта. Не подменять требование просто новыми таблицами в существующей БД без отдельного согласования.
- Не создавать автоматические связи между производственными значениями этого блока и другими модулями учёта. Отметка ремонта в отчёте не должна менять состояние техники в другом модуле.
- Пользователь выбрал единый график смен. Переиспользовать правило календаря/сервис расписания существующего сайта, если он есть, сохраняя наряды в отдельной БД. Не заводить расходящийся параллельный график и не переносить производственные данные между базами. Конкретный способ согласовать с реальной архитектурой.
- Для входа и определения прав использовать существующие механизмы сайта, если архитектура это позволяет. Изоляция бизнес-данных не должна заставлять мастера проходить дополнительную регистрацию.
- Сохранять автора, время сохранения и версии данных. Изменения общих справочников также желательно протоколировать.
- Удаление техники или причины из актуального списка не должно удалять историю. Предпочтительно скрытие/архивирование справочных записей со стабильными идентификаторами.

## 3. Справочники и настройки

### 3.1. Экскаваторы

Пользователь и мастера самостоятельно добавляют экскаваторы и задают:

- номер;
- тип;
- направление погрузки: ЖД или авто;
- основной вид самосвала для авто, используемый по умолчанию.

Начальные типы: **ЭКГ-10, ЭКГ-12К, ЭКГ-15, ЭКГ-20, P&H**.

За один отчётный период у экскаватора только одно направление. Одновременная погрузка на ЖД и авто в одной смене не требуется. Перевод техники между направлениями не должен менять классификацию старых отчётов.

Не использовать вымышленные номера, типы и значения из макета как реальные стартовые данные.

### 3.2. Нормативы времени погрузки

Нормативы вводятся и сохраняются в отдельном месте один раз. Они общие для мастеров; изменения редки. При ежедневном заполнении норматив подставляется автоматически.

| Направление | Единица погрузки | От чего зависит норматив |
| --- | --- | --- |
| ЖД | Один думпкар | Тип экскаватора |
| Авто | Один самосвал | Тип экскаватора и грузоподъёмность самосвала |

Для авто предусмотрены **БЕЛАЗ 90 т, 130 т и 240 т**. У каждого типа экскаватора свой норматив для каждой из этих категорий.

Реальные числовые нормативы пользователь пока не предоставил. Не изобретать их и не переносить демонстрационные значения в рабочую БД. Отсутствующий норматив обозначать как отсутствие настройки, а не как нулевую длительность.

Техническое предложение: сохранять в версии отчёта использованный норматив и единицу/формат времени. Правка общего справочника действует на последующие отчёты, а не переписывает прошлые. Для исправления старого периода по умолчанию сохранять его исторический норматив; возможность отдельной коррекции самого исторического норматива требует решения.

### 3.3. Причины невыполнения

- Редактируемый список причин.
- Можно выбрать одну или несколько причин и добавить свободное пояснение.
- Обязательная известная причина для начального списка: **«Аварийный ремонт»**.
- Другие причины вводят пользователь/мастера. Предложенные в макете примеры не являются утверждённым перечнем.
- Причины не обязательны для сохранения и отправки, в том числе при невыполнении наряда.

## 4. Форма отчёта

Два раздела: **«Железнодорожный транспорт»** и **«Автотранспорт»**.

Сверху видны выбранный период работы, номер смены 1–4 и состояние отчёта. Кнопка «История» открывает прошлые отчёты с выбором даты/смены; история не занимает основную таблицу. Настройки справочников находятся отдельно от ежедневного ввода.

Два основных действия: **«Отправить предварительный»** и **«Отправить итоговый»**. Каждое сначала сохраняет соответствующую версию. Прочие действия: «Сбросить параметры», «История», настройки. В режиме исправления старого отчёта сохранение и повторная отправка разделены, см. раздел 8.

Порядок основных показателей слева направо:

| Поле | Содержание |
| --- | --- |
| Экскаватор | Номер; тип можно показывать вторичной строкой |
| Наряд план | Заданный объём горной массы, м³ |
| Наряд факт | Фактически отгруженный объём, м³ |
| Погрузка — норматив | Справочное значение из настроек |
| Погрузка — факт | Готовое среднее время за смену из исходной системы |
| Ожидание | Суммарное время ожидания за смену |
| Причины невыполнения | Выбранные причины и необязательное пояснение |
| Отметки на всю смену | «Ремонт», «Без бригады» |

На ЖД ожидание называется **«Ожидание порожняка»**, на авто — **«Ожидание самосвалов»**. Ожидание вводится одним суммарным показателем по экскаватору.

Норматив должен визуально отличаться от редактируемого факта. Его не требуется вводить заново в каждой смене.

### 4.1. Несколько видов самосвалов

Обычно экскаватор грузит один вид самосвалов; редко — два.

1. В форме заранее выбран основной вид из настроек экскаватора.
2. Кнопка **«+ Другой самосвал»** добавляет ещё один вид внутри того же экскаватора.
3. Для каждого вида показываются свой норматив и отдельное фактическое среднее время. Исходная система выдаёт мастеру эти средние отдельно по видам самосвалов.
4. Любой вид, в том числе основной, можно убрать одной кнопкой.
5. Пример: по умолчанию 130 т, фактически всю смену 240 т — добавить 240 т, убрать 130 т и заполнить время.
6. Если 130 т остался пустым, а заполнено только время 240 т, пустой вид не учитывается в показателях.
7. **План и факт по горной массе общие по экскаватору за смену.** Не дублировать объёмы для каждого вида.
8. В исходной системе объём по видам самосвалов недоступен: есть только общий факт по экскаватору.

## 5. Форматы времени и удобство ввода

Все показатели времени погрузки пользователь уточнил как десятичные минуты. Единицы ожидания не меняются.

| Показатель | Единица и формат | Пример |
| --- | --- | --- |
| Погрузка одного думпкара | Десятичные минуты | 1,5 = 1 мин 30 сек |
| Ожидание порожняка | Десятичные часы | 1,85 = 1 ч 51 мин |
| Погрузка одного самосвала | Десятичные минуты | 8,72 = 8 мин 43,2 сек |
| Ожидание самосвалов | Часы и минуты | 2:30 = 2 ч 30 мин |

Фактическая погрузка — уже рассчитанное **среднее из исходной системы**. Мастер не вводит отдельные рейсы и не рассчитывает это среднее вручную. Ожидание — сумма за смену, а не среднее ожидание одной подачи.

При просмотре первого макета пользователь отметил единственное затруднение: ввод знаков препинания. Подготовлен второй вариант:

- погрузка ЖД и авто: целая и дробная части десятичных минут, запятая уже отображается между полями;
- авто, ожидание: два цифровых поля «ч» и «мин»;
- ЖД, ожидание: целая и дробная части десятичных часов, запятая уже отображается между полями;
- переход между полями обычной клавишей Tab; принудительный автоматический перескок не требуется;
- норматив показывается в соответствующем формате;
- изменение формата в будущем не должно менять смысл ранее сохранённой длительности.

Технические правила для предложенного ввода:

- дробную часть погрузки не обрабатывать как обычное целое число: `5` после запятой означает 0,5 минуты, `05` — 0,05 минуты;
- оба поля пустые — показатель отсутствует, а не равен нулю;
- при заполнении только одной части вторая часть длительности трактуется как ноль; явный ноль остаётся нулём;
- ограничение 0–59 применяется только к правой части ожидания авто в формате ч:мин; к дробной части десятичного значения это ограничение не относится;
- не угадывать расположение запятой в записи `185` и не менять единицы молча;
- технический способ хранения длительностей должен позволять сопоставимые расчёты и воспроизведение согласованных единиц без потери точности.

## 6. Ремонт и отсутствие бригады

| Ситуация | Наряд и учёт |
| --- | --- |
| Плановый ремонт всю смену | Достаточно отметки «Ремонт»; наряд обычно 0, показатели исключаются из производственных расчётов. Ввод 0 не является обязательным условием |
| Без бригады всю смену | Достаточно отметки «Без бригады»; показатели исключаются из производственных расчётов |
| Плановый ремонт часть смены | Мастер вводит уже уменьшенный заданный наряд и фактический объём; строка участвует в расчётах |
| Аварийный ремонт | Незапланированная остановка; причина невыполнения, а не исключающий статус; заданный план и реальный факт сохраняются и участвуют в расчётах |

Пример аварийного ремонта: план 3700 м³, факт 1500 м³ — выполнение около 40,5%, причина «Аварийный ремонт».

Система не уменьшает наряд автоматически из-за аварии и не делит его автоматически пополам при частичном плановом ремонте.

Отметки на всю смену должны быть однозначны. Техническое предложение — хранить одно состояние строки, даже если в интерфейсе оно выбирается флажками. История строк с исключающими состояниями сохраняется: исключение из расчёта не означает удаление из БД.

## 7. Неполные данные и автоматический комментарий

### Согласовано

- План, факт, время погрузки и ожидание можно оставлять пустыми.
- Неполнота не мешает ни предварительной, ни итоговой отправке. **Мастер сам выбирает, итоговый отчёт или нет.** Заполненность полей и время на часах не определяют этот статус автоматически.
- Мастер может отправить предварительный отчёт, например, в 06:30: указать известные причины, оставив факт объёма пустым. Ближе к 08:00 он дополняет тот же отчёт и отправляет итоговую версию. Ранняя отправка допустима; пример 06:30 не является обязательным расписанием.
- Для отсутствующего плана или факта в отчёте и сообщении бота выводится **«не заполнено»**.
- Пустое значение не преобразуется в 0.
- Если по экскаватору отсутствует план или факт, его процент выполнения не вычисляется.
- Выбор причины и ввод пояснения не обязательны.
- Если оба объёма заполнены и факт меньше плана, автоматически выводится **«Наряд не выполнен»**. Отсутствие выбранной причины не блокирует отправку.

Автоматический комментарий описывает сравнение чисел и не должен придумывать причину. Выбранные мастером причины и его пояснение сохраняются отдельно. При обновлении значений комментарий пересчитывается для новой версии; содержимое старой версии остаётся историческим.

Не писать «Наряд не выполнен» только из-за отсутствующего факта или плана. У исключённых строк «Ремонт»/«Без бригады» показывается соответствующее состояние.

Для отсутствующего времени технически также сохранять признак отсутствия. Внешнее обозначение незаполненного времени окончательно включить в согласование вида сообщения MAX; в аналитике такие значения не становятся нулевыми длительностями.

Отказ от обязательных полей и обязательных причин не означает разрешения незаметно искажать некорректную числовую запись. Ошибку формата показывать рядом с полем; не заменять ошибочную строку нулём или произвольной длительностью.

## 8. Рабочий цикл, сохранение, версии, история и сброс

### 8.1. Основной сценарий

1. Мастер видит общий парк и ясно обозначенный период работы: день/ночь, дата или диапазон дат, номер смены 1–4.
2. Переносит доступные показатели из производственной системы.
3. Сам выбирает **«Отправить предварительный»** или **«Отправить итоговый»**.
4. Система сохраняет версию с выбранным видом. При настроенной интеграции передаёт её в MAX по правилам рассылки.
5. Показывает фактический результат сохранения и отправки. Значения остаются в форме.
6. При дополнении отчёта за ту же смену сохраняется новая версия того же отчёта.
7. Следующий мастер для своего нового периода выбирает: сбросить сменные значения до значений по умолчанию либо использовать оставшиеся значения как основу и отредактировать их.

Перенос значений в следующий период создаёт рабочую форму нового отчёта. Он не переносит прежние признаки «итоговый»/«отправлен» и не переписывает прошлую смену. Редактируемая форма и архивная запись должны быть разными сущностями.

### 8.2. Предварительный и итоговый отчёт

| Вид | Назначение | Участие в аналитике |
| --- | --- | --- |
| Предварительный | Сообщить имеющиеся сведения до окончательного заполнения; поля могут быть пустыми | Сохраняется в истории, в производственные итоги не включается |
| Итоговый | Мастер считает ввод за смену завершённым; отдельные поля тоже могут оставаться пустыми | Используется последняя сохранённая итоговая версия этого периода |

Оба вида доступны мастеру по его решению, без автоматического определения по часам или проценту заполненности. Предварительная отправка необязательна: можно сразу отправить итоговый.

Если после итоговой сохранена предварительная версия, в аналитике остаётся предыдущая итоговая. Если итоговой версии нет, период в производственной аналитике не учитывается; его отсутствие не трактуется как нулевой результат работы. В истории видно, что итоговый ещё не сформирован.

В самой предварительной версии можно показывать вычислимые показатели и причины по имеющимся данным. Это не делает её источником итоговой аналитики.

### 8.3. Версии и результат отправки

- Новый период — новый отчёт.
- Сохранение изменённых данных за тот же период — новая версия прежнего отчёта.
- Предыдущие версии сохраняются.
- Аналитика использует **последнюю сохранённую итоговую версию каждого периода**, без удвоения объёмов.
- Успешность доставки MAX не меняет выбранную для аналитики итоговую версию.
- Несохранённые изменения формы не меняют историю и аналитику.
- Статус отправки старой версии не означает, что отправлены новые изменения.

Нужно независимо хранить: вид версии (предварительная/итоговая), факт исправления и состояние доставки. Например, отчёт может быть итоговым, исправленным и ещё не отправленным в MAX.

### 8.4. История и исправления

1. Мастер нажимает «История», находит нужную дату/смену и открывает сохранённый отчёт.
2. Любой мастер может нажать «Исправить».
3. Исправление сохраняется новой версией того же периода, с автором, временем и доступным сравнением «что было / что стало».
4. В этом режиме сохранение исправления **не запускает рассылку автоматически**.
5. Отдельная кнопка позволяет отправить уже сохранённую исправленную версию.
6. Исправленный итоговый отчёт заменяет прежний итоговый в аналитике после сохранения, независимо от повторной отправки.
7. Предыдущая версия остаётся доступной; история не перезаписывается.

Исправление должно быть заметно и спустя время:

- в истории — **«Исправлен»**, автор и время;
- если прежняя версия была отправлена, а новая ещё нет — **«Исправлен после отправки. Новая версия в MAX не отправлена»**;
- при повторной отправке — обозначение **«Исправленный отчёт»** и период, к которому он относится; окончательное оформление сообщения согласуется отдельно.

Техническое предложение: исправление сохраняет вид исходной версии, если мастер явно не выбрал другой вид. Изменение предварительного отчёта не должно незаметно включать его в аналитику. Обычное дополнение предварительного отчёта до первой итоговой версии само по себе не является исправлением ранее принятого итога; не выводить «Исправлен» только по условию «номер версии больше 1».

Работа с историей не должна незаметно заменять текущую форму другой смены. Режим исправления старого периода и его даты должны быть явно видны.

### 8.5. «Сбросить параметры»

Сброс очищает текущую рабочую форму:

- план и факт по горной массе;
- фактическое время погрузки и ожидание;
- выбранные причины и пояснения;
- отметки «Ремонт» и «Без бригады»;
- дополнительные виды самосвалов.

Остаются/подставляются из настроек:

- общий список экскаваторов;
- их типы и направления;
- общие нормативы;
- основной вид самосвала по умолчанию.

После сброса числовые поля пустые, а не автоматически нулевые. Архив не меняется. Действующий итог в аналитике меняется только после сохранения новой итоговой версии соответствующего периода; сброс и сохранение предварительной версии его не заменяют.

### 8.6. Технические предложения для надёжности

- У периода/отчёта и каждой его версии — стабильные идентификаторы. Идентичность отчёта не определяется только временем отправки или совпадением значений формы.
- Двойной клик одной операции не должен создавать две версии и повторную рассылку.
- Технический повтор доставки существующей версии не создаёт новую производственную версию.
- Желательно сохранять черновик, чтобы обновление страницы не теряло ввод. Черновик не участвует в аналитике.
- Открытая форма остаётся привязанной к выбранному периоду при наступлении 08:00 или 20:00. Нельзя автоматически переименовать ночной отчёт в дневной во время ввода.
- Предоставить простой выбор нужного периода, включая предыдущую смену, для запоздалого заполнения. При переходе к следующему периоду явно показывать его даты и номер смены.
- При одновременной работе двух вкладок/мастеров не допускать незаметного затирания более свежей сохранённой версии. Использовать механизм проверки версии, подходящий проекту.

## 9. MAX: подготовленная интеграция и отдельный этап рассылки

### 9.1. Что уже определено

- Предварительные и итоговые версии должны поддерживать отправку через бота MAX.
- Исправление старого отчёта сохраняется без автоматической рассылки; повторная отправка — отдельное действие.
- Исправленная версия при отправке явно обозначается как исправленная.
- Архитектура должна позволять отправку одной версии в несколько групп, в том числе 2–3 группы, за одно действие мастера.

**Какие именно отчёты в какие группы будут отправляться, пользователь решит позже.** Не считать согласованными одинаковый текст для всех групп, один общий список адресатов для всех видов отчёта или отправку во все группы, где состоит бот.

Вид сообщения тоже отложен. Не утверждены макет, объём детализации, разбиение на сообщения и представление таблицы/вложений. Уже определённые смыслы сохраняются в любом будущем формате: период и номер смены, предварительный/итоговый вид, отметка исправления, «не заполнено» для отсутствующих объёмов, причины и автоматический комментарий.

### 9.2. Надёжность доставки — технические требования к реализации

- Сначала сохранить конкретную версию, затем передать её в отправку. Бот читает зафиксированные данные этой версии.
- Ошибка MAX не уничтожает сохранённый отчёт и не исключает сохранённую итоговую версию из аналитики.
- Различать «не удалось сохранить» и «сохранено, но не удалось отправить».
- Доставку учитывать по каждой паре «версия × адресат»; при разбиении длинного отчёта — учитывать и части сообщения.
- Успешную доставку в часть групп не показывать как успешную доставку во все. Возможное обозначение: «Отправлено в 2 из 3 групп» с деталями по получателям.
- Повторять подтверждённо неудачную доставку отдельно; уже успешные адресаты не должны получать дубли при таком повторе.
- Если результат запроса неизвестен, показывать неопределённое состояние; не считать его доказанным отказом и не обещать отсутствие дублей без механизма проверки.
- Хранить идентификаторы отправленных сообщений, время, результат и ошибки попыток. Успех старой версии не помечает новую как отправленную.
- Получатели и правила маршрутизации должны быть конфигурацией, а не именами групп, зашитыми в код.
- Для каждой отправки фиксировать фактически выбранных адресатов, чтобы последующая правка настроек не меняла историю доставок.

### 9.3. Порядок подключения

Сначала изучить код существующего бота и механизмы сайта. До согласования получателей и оформления реализовать сохранение, статусы и интерфейс интеграции. При отсутствии настроенной рассылки правдиво показывать, что версия сохранена, а отправка не настроена. Не имитировать успешное сообщение в MAX.

В текущем ТЗ отправку запускает мастер кнопкой. Близость к 08:00/20:00 описывает рабочий процесс; обязательного автоматического расписания пользователь не задал. Автоматизация — отдельное возможное расширение.

Реальные сообщения в рабочие группы не использовать для тестирования без согласованного адресата. Возможности и ограничения API повторно проверить при реализации.

Официальные ориентиры, проверенные 29.09.2026:

- Отправка в чат по его идентификатору: https://dev.max.ru/docs-api/methods/POST/messages
- Получение идентификаторов чатов: https://dev.max.ru/docs-api/use-cases/getting-chat-id

Отправка в несколько групп реализуется отдельными запросами к выбранным чатам. Эти ссылки не подтверждают, что существующий бот rapmas.ru уже умеет такую рассылку.

## 10. Смены, единый график и обозначение периода

### 10.1. Рабочий график

- День: 08:00–20:00.
- Ночь: 20:00–08:00 следующего календарного дня.
- Четыре смены/бригады: № 1–4.
- Цикл бригады: день → ночь → отсыпной → выходной.
- Последовательность дневных бригад 1 → 2 → 3 → 4; ночные следуют по порядку со сдвигом.
- Используется **единый график**; номер смены в отчёте подставляется по нему.

В терминах данных «бригада» — номер 1–4. В интерфейсе использовать привычное пользователю название «1 смена», «2 смена» и т. д., отдельно от признака «день/ночь».

Опорное описание пользователя на дату интервью: 29.09.2026 в день № 2, 30.09.2026 в день № 3, затем в ночь 30.09–01.10 № 2. Перед начальным заполнением календаря сверить это с единым графиком проекта. При расхождении показать конкретное расхождение; не придумывать новую опору.

### 10.2. Период работы и время отправки

После первоначального замечания о разных границах пользователь уточнил рабочий сценарий: дневной отчёт формируется ближе к 20:00, ночной — ближе к 08:00. Утром допустима более ранняя предварительная отправка, затем дополнение и итоговая отправка за **ту же смену**.

Ранняя отправка не создаёт отдельную смену и не меняет её начало/конец. Поздняя отправка тоже относится к выбранному периоду работы, а не автоматически к смене, которая идёт в момент нажатия.

Сохранять отдельно начало/конец периода работы и время сохранения/отправки. Отдельные смещённые интервалы сбора данных пользователь не задал; не изобретать, например, 06:30–18:30.

### 10.3. Подпись ночного отчёта и поиск в истории

Ночной отчёт показывать обеими датами и номером смены, например:

**«Ночь с 29.09 на 30.09 · 2 смена»**.

Это условный пример формата: пользователь сказал «если в ночь будет вторая смена». Он не заменяет опорный график из раздела 10.1.

Дневной отчёт: дата, обозначение «День» и номер смены. В данных хранить полные даты с годом, обе границы периода и номер бригады. При переходе месяца/года подпись должна оставаться однозначной.

Не требовать от мастера выбора единственной даты вместо диапазона ночи. Для истории предусмотреть поиск ночного отчёта по обеим затронутым датам. При будущей суточной аналитике правило отнесения переходящей ночи к одним суткам согласовать отдельно, если такой показатель понадобится; хранение интервала уже позволяет это сделать.

Техническое предложение: календарь и подписи рассчитывать в настроенном часовом поясе предприятия. Проверить настройку проекта; время браузера пользователя или сервера не должно незаметно сдвигать границы смен.

Номер бригады сохранять в отчёте как историческое значение. Изменение календаря в будущем не должно автоматически переносить старые результаты между бригадами.

## 11. Аналитика и ограничения исходных данных

Цель накопления данных — последующий анализ выполнения нарядов, времени погрузки и ожидания с группировками по периодам, экскаваторам, типам техники, направлениям погрузки и **сменам/бригадам № 1–4**. Для авто сохранять и категорию самосвала.

Источник производственной аналитики — **последняя сохранённая итоговая версия каждого периода**. Предварительные версии доступны для просмотра в истории, но не подмешиваются в итоги. При отсутствии итоговой версии не создавать нулевые показатели за этот период. При сравнении смен показывать охват итоговыми отчётами, чтобы отсутствие отчётов не выглядело хорошим или плохим производственным результатом.

Полноценный интерфейс будущей аналитики ещё не спроектирован. При реализации ввода необходимо обеспечить правильную структуру и доступность данных, не усложняя повседневную форму дополнительными рейсами и ручным распределением объёмов.

### 11.1. Выполнение наряда по экскаватору

При наличии обоих значений и положительном плане:

`выполнение, % = факт / план × 100`.

Пропущенный план/факт — нет расчёта. При нулевом плане процент математически не определён: техническое предложение — показывать «не рассчитывается», сохраняя сам факт. Перевыполнение не обрезать до 100%.

Строки «Ремонт» и «Без бригады» исключаются из производственного расчёта. Аварийный ремонт не исключает строку.

**Общий процент при частично заполненных строках согласован.** Рассчитывать его только по строкам с заполненными планом и фактом:

`общее выполнение, % = сумма(факт) / сумма(план) × 100`.

В обеих суммах использовать один и тот же набор участвующих строк. Не считать среднее арифметическое процентов и не подставлять 0 вместо пропуска. При отсутствии пригодных строк или нулевой сумме планов процент не вычислять.

Если обе величины заполнены у 8 из 10 работающих экскаваторов, показывать процент по этим восьми и пометку **«Данные неполные: заполнено 8 из 10»**. В число ожидаемых строк не включать исключённые состояния «Ремонт» и «Без бригады». Аварийный ремонт остаётся в расчёте и в числе ожидаемых строк. Неполнота не блокирует сохранение и отправку.

### 11.2. Среднее время с весом по объёму

Пользователь предложил использовать общий «Наряд факт» как вес вместо количества рейсов. Количество рейсов не добавляется в обязательный ввод.

Показатель следует называть **«Среднее время погрузки, взвешенное по объёму отгрузки»**, а не точным средним по всем рейсам.

`среднее = сумма(среднее время за смену × факт м³) / сумма(факт м³)`.

До расчёта привести длительности к сопоставимой единице. В одном расчёте участвует только последняя сохранённая итоговая версия каждого периода и только пригодные для выбранного показателя данные.

Согласованное правило для авто:

- Если фактическое время заполнено по одному виду самосвалов, использовать общий факт экскаватора как вес.
- Если время заполнено по двум видам, сохранить оба времени, но исключить эту запись из среднего, взвешенного по объёму: распределение общего объёма неизвестно. Технически проверять условие «более одного заполненного вида», чтобы возможное добавление третьего вида не обходило это правило.
- Пустой основной вид плюс один заполненный дополнительный вид считаются одним заполненным видом.
- Исключение из этого среднего не исключает план/факт из расчётов объёма и выполнения наряда.
- Показывать охват, например «Учтено 18 из 20 смен». Точную единицу охвата при группировке нескольких экскаваторов называть явно: записи «экскаватор × период» или периоды, а не смешивать их.

Для ЖД также можно использовать факт как вес, поскольку пользователь выбрал этот подход для будущей аналитики. Не добавлять ручной ввод количества думпкаров без отдельной необходимости.

Технически: отсутствие времени или факта исключает запись только из соответствующего среднего; факт 0 не даёт положительного веса. Если сумма пригодных весов 0, результат не вычисляется. Не делить общий факт между самосвалами произвольными долями и не удваивать его.

Ограничение данных: точный средний показатель по всем рейсам и объёмы по категориям самосвалов восстановить из этих записей нельзя. Выбранное упрощение должно оставаться видимым в описании аналитики.

## 12. Границы реализации и отложенные решения

### Реализовать по этому ТЗ

Простую форму и справочники; отдельную БД; привязку к сменам единого графика; рабочие черновики и сброс; предварительные/итоговые версии; историю и исправления; расчёт выполнения наряда и признак неполноты; корректный набор данных и правила отбора для будущей аналитики; состояния и интерфейс подключения отправки.

Полноценный конструктор аналитики, дополнительные обязательные производственные показатели и ввод отдельных рейсов в этот этап не входят.

### Отдельный этап по решению пользователя

1. **Какие отчёты в какие группы MAX отправлять.** Не определены конкретные адресаты, правила для предварительных/итоговых/исправленных версий и одинаковость содержимого между группами.
2. **Окончательный вид отчёта в MAX:** состав и порядок отображения, сообщение/вложение, поведение длинных отчётов.
3. **Экраны будущей аналитики и экспорт.** Данные и известные формулы подготовить сейчас; детальное представление согласовать при развитии аналитики.
4. Автоматическая отправка по расписанию, если она понадобится. Сейчас предусмотрены действия мастера.

Эти решения не препятствуют реализации формы, базы, истории и подготовки интеграции. Реальную маршрутизацию и окончательное сообщение подключать после соответствующего согласования.

### Решить технически после изучения репозитория

- Тип отдельной БД, миграции, резервное копирование и подключение к действующей авторизации.
- Переиспользование единого графика, проверка календарной опоры и часового пояса.
- Автосохранение и защита от конфликтов черновиков/версий.
- Хранение исторических значений справочников и нормативов. Рекомендуемый вариант: использовать норматив сохранённого периода при его исправлении; не подменять его сегодняшним автоматически.
- Возможности существующего бота и безопасный способ тестирования отправки.

Это задачи обследования проекта, а не просьба к пользователю заново отвечать на уже согласованные вопросы.

| Версия отчёта | ID/номер версии, предварительная или итоговая, автор/время; неизменяемые значения и снимки справочных данных; связь с предыдущей версией и признак исправления |
| Строка экскаватора | Экскаватор, исторические номер/тип/направление, состояние, план и факт nullable, ожидание nullable, причины и пояснение |
| Показатель погрузки | Направление/категория самосвала, норматив версии, фактическое среднее nullable |
| Рабочий черновик | Данные редактируемой формы, выбранный период, сведения для восстановления/защиты от конфликта; отдельно от сохранённых версий |
| Адресат/правило MAX | Расширяемая конфигурация будущей маршрутизации; значения не задаются догадкой |
| Отправка/доставка | Версия, фактические адресаты, результат по каждому адресату/части, идентификаторы сообщений, подтверждённое время, попытки/ошибки |
| Изменения | Автор, время и доступные предыдущие/новые значения; могут получаться из сохранённых версий без дублирования всех данных |

Не хранить «не заполнено» в числовом столбце: это отображение отсутствующего значения. Не связывать историческую классификацию только с текущим изменяемым справочником. Пустые и нулевые значения различать на всех слоях.

Сохранение версии и её строк должно быть целостной операцией: не оставлять наполовину сохранённый отчёт. Доставка MAX выполняется после сохранения и может иметь собственные повторные попытки.

| Итоговая отправка после предварительной | Новый итог той же смены; аналитика учитывает его один раз |
| Итоговый с пустыми полями | Разрешён по решению мастера; неполнота обозначена, отсутствующие значения не превращаются в нули |
| Итоговый, затем новая предварительная версия | В аналитике остаётся последняя итоговая; последняя предварительная видна в истории |
| За период есть только предварительные версии | Нет итоговых производственных показателей за этот период, отсутствие не считается нулевой работой |
| Исправление старого итогового любым мастером | Новая итоговая версия, метка «Исправлен», автор/время и прежние значения доступны; аналитика обновлена, рассылка не запускается сама |
| Повторная отправка исправленного | Отправляется сохранённая исправленная версия с соответствующей пометкой; новая производственная версия только из-за доставки не создаётся |
| Ночная смена через две даты | Заголовок содержит обе даты и номер смены; период доступен через историю по обеим датам |
| Открытая ночная форма после 08:00 | Остаётся привязанной к выбранной ночи, даты не переключаются незаметно |
| Переход следующего мастера к новому периоду без сброса | Значения могут быть основой нового черновика; прежний архив цел, статус итоговости/доставки не копируется |
| Группировка по сменам № 1–4 | Используются номера бригад, сохранённые в итоговых отчётах; изменение текущего графика не меняет историю |
| Рассылка в несколько групп после настройки | Результат по каждой группе; частичная доставка не равна полному успеху |
| Повтор подтверждённой ошибки в одной группе | Уже успешные адресаты повторно не получают ту же версию из-за технического повтора |
| MAX пока не настроен | Версия сохраняется; явно видно, что реальная отправка не выполнена; нет вымышленных адресатов |
| Изоляция данных | Наряды сохраняются в отдельной БД; изменение ремонта/справочника в этом блоке не изменяет производственные данные других модулей |

## 17. Дополнение от 09.10.2026: получение фотографии на сайте и накопление исходных показателей

Статус этого раздела: **локальный диагностический пилот распознавания реализован; автоматический перенос и накопление структурированных показателей ещё не реализованы**. Он дополняет форму отчёта, но не отменяет проверку мастером, версии и правила отбора итоговых отчётов.

### 17.1. Канал и доступ

- Мастер прикладывает фотографию непосредственно на сайте rapmas с телефона или планшета. Входная фотография через личный диалог MAX отменена последующим решением пользователя.
- Блок загрузки полностью скрыт на компьютере. Сервер принимает запрос только из мобильного интерфейса; камера и выбор готового снимка разрешены.
- Пользоваться распознаванием могут все существующие учётные записи сайта, которым доступен раздел «Отчёт за смену».
- Мастер фотографирует крупно только раздел «Главный карьер»; Северный карьер и СКМ не входят в текущий этап.
- Исходная фотография после распознавания не сохраняется. Структурированные показатели при будущем подтверждённом импорте должны храниться отдельно от отчёта.

### 17.2. Полный исходный снимок

- Бот сохраняет не только поля, которые сейчас нужны сменному отчёту, а **все показатели таблицы по текущему объёму — разделу «Главный карьер»**: дату, смену, номер экскаватора, производственную категорию, план, факт, отклонение, показатели качества, времена погрузки и итоговые строки «Факт»/«Наряд».
- Обозначение смены в исходной таблице не является номером бригады: `Смена 2` означает дневной период 08:00–20:00, `Смена 1` — ночной период 20:00–08:00.
- Номер бригады 1–4 всегда определяется единым неизменным календарём rapmas.ru. Значение из фотографии не может заменить или исправить номер бригады.
- Дата дневной исходной таблицы является датой дневного периода. Для ночной таблицы указывается дата, на которую приходится больше часов, то есть дата окончания ночи; например, таблица с датой 10.10.2026 и `Смена 1` относится к периоду с 20:00 09.10.2026 до 08:00 10.10.2026.
- Контрольная опора календаря: 09.10.2026 с 08:00 до 20:00 работает бригада № 4; с 20:00 09.10.2026 до 08:00 10.10.2026 работает бригада № 3. Действующая реализация `lib/shift-calendar.ts` соответствует этой опоре.
- Северный карьер и Западный карьер остаются за границами текущего этапа. Их наличие на фотографии не означает разрешение добавлять их в учёт.
- Для каждого распознанного значения сохраняются исходное обозначение столбца, исходный текст и нормализованное значение. Пустое, непрочитанное и числовой ноль различаются.
- Источник должен быть трассируемым: пользователь сайта, время получения, контрольная сумма фотографии, версия схемы распознавания и список предупреждений.
- Исходные показатели хранятся отдельно от производного черновика сменного отчёта, чтобы будущая статистика могла использовать категории без потери детализации и без повторного распознавания фотографии.

### 17.3. Нормализация транспорта и времени

- Столбец `Б75313` означает БЕЛАЗ грузоподъёмностью **240 т**.
- Столбец `Б75131` означает БЕЛАЗ грузоподъёмностью **130 т**.
- Все показатели времени погрузки в исходной таблице заданы в десятичных минутах. Запятая является десятичным разделителем, а не разделителем минут и секунд: например, `8,72` означает 8,72 минуты, то есть 8 минут 43,2 секунды; `5,30` означает 5,30 минуты, то есть 5 минут 18 секунд.
- В исходном слое значение времени сохраняется в десятичных минутах без потери указанной в таблице точности.
- Вместе с нормализованной грузоподъёмностью сохраняется исходное обозначение модели из таблицы.
- Если у одного экскаватора заполнены оба столбца `Б75313` и `Б75131`, оба фактических времени сохраняются и переносятся в сменный отчёт отдельно: для БЕЛАЗ 240 т и БЕЛАЗ 130 т. План и факт остаются одной общей суммой по экскаватору и не дублируются по видам самосвалов.
- `Ср.вр. погр. думпк., мин.` сохраняется как фактическое среднее время погрузки думпкара в минутах.
- В сменный отчёт время погрузки переносится в тех же десятичных минутах, без округления до целых секунд. Исходный снимок и исходное распознанное значение при этом не изменяются.

### 17.4. Качество и подтверждение

Уточнение пользователя: входной канал — прикрепление фотографии непосредственно на сайте rapmas с телефона, вместо личного диалога MAX. Требования к ограничению пользователей, полному исходному снимку и подтверждению сохраняются. Локальный пилот 10.10.2026 только показывает сырой результат OCR; накопление исходных показателей и перенос в черновик ещё не реализованы. См. `docs/production-ocr.md`.

- До распознавания проверяются размытие, разрешение таблицы, наклон, наличие заголовков и полнота раздела «Главный карьер».
- Фото недостаточного качества отклоняется; сомнительные цифры нельзя угадывать или заменять нулём.
- После распознавания бот показывает мастеру период, число найденных экскаваторов, предупреждения и способ открыть проверку результата.
- Распознавание само по себе не создаёт предварительную или итоговую версию и не включает данные в аналитику.
- Только подтверждённая мастером часть данных переносится в черновик сайта. Сохранение предварительной/итоговой версии остаётся отдельным действием мастера.
- Импорт применяет изменения как ограниченный набор распознанных полей и не очищает уже введённые комментарии, причины, ожидание или состояния техники.

### 17.5. Подготовка к статистике

- Накопленные исходные данные должны позволять в будущем строить статистику по датам, сменам, экскаваторам, категориям горной массы, плану/факту, показателям качества и времени погрузки.
- Производные значения для сменного отчёта не заменяют полный исходный снимок.
- Каждая производственная категория одного экскаватора хранится в исходной базе отдельно. Например, наряд по руде и наряд по вскрыше — разные записи и остаются различимыми для будущей статистики.
- Для единой строки экскаватора в сменном отчёте план рассчитывается как сумма планов его производственных категорий, а факт — как сумма фактов этих категорий. План из исходной таблицы в тысячах м³ перед суммированием явно переводится в м³. Итоговые строки таблицы «Факт»/«Наряд» не прибавляются повторно к строкам экскаваторов.
- Срок хранения исходной фотографии и необходимость хранить её после подтверждения остаются открытым решением. Структурированные показатели и сведения об источнике должны сохраняться независимо от этого решения.

## 18. Дополнительные показатели действующего сменного отчёта

**Статус: поля, нормативы и единицы перенесены на рабочий сервер 09.10.2026; итоговое изображение MAX локально реализовано и принято 10.10.2026. Доступ к разделу на рабочем сервере пока сохранён только для администратора.**

- Действующий Excel-отчёт используется только как справочный образец состава показателей. Импортировать сам Excel-файл в сайт не требуется.
- В блок «Отчёт за смену» планируется добавить редактируемые вручную показатели `Загрузка, %` и `Выход негабарита, %`. При будущем импорте фотографии бот переносит готовые значения, но сайт не рассчитывает их самостоятельно.
- `Выход негабарита, %` применяется только при погрузке на автотранспорт. Для ЖД-направления это поле не требуется; отсутствие такого показателя нельзя подменять числовым нулём.
- Для автоэкскаватора сохраняется одно общее значение выхода негабарита независимо от того, какие виды самосвалов он грузил. Если из нескольких исходных категорий получены разные значения, система не выбирает и не усредняет их автоматически: итог вручную указывает мастер.
- Выход негабарита вводится как десятичный процент от 0 до 100 включительно, не более двух знаков после запятой. Пустое значение отличается от `0 %`.
- `Загрузка, %` применяется ко всем экскаваторам: и при погрузке на автотранспорт, и при погрузке в ЖД транспорт. Для одного экскаватора сохраняется одно общее значение независимо от производственной категории и вида самосвала.
- `Загрузка, %` вводится как десятичный процент от 0 до 999,99 включительно, не более двух знаков после запятой. Значения свыше 100 % разрешены; пустое значение отличается от `0 %`.
- Оба показателя входят в сохраняемый снимок версии отчёта и отображаются в истории. `Выход негабарита, %` показывается в итоговой картинке для автоэкскаваторов; `Загрузка, %` пока намеренно скрывается из отчёта MAX, но остаётся в инфраструктуре и БД.
- Остальные показатели сводной таблицы Excel не добавляются автоматически: текущая задача ограничена загрузкой и выходом негабарита.

## 19. Первичное заполнение нормативов погрузки

**Статус: источник, сопоставление и значения согласованы; справочник перенесён на рабочий сервер 09.10.2026. Заполнено 11 пустых нормативов, два просмотренных конфликта заменены значениями PDF; повторный запуск подтвердил отсутствие дальнейших изменений.**

- Источник нормативов один: предоставленный PDF. Используются только серые строки `Время погрузки а/с ...` и `Время погрузки думпкар`.
- Значение выбирается на пересечении строки вида транспорта и столбца типа экскаватора в группах `Погрузка в автотранспорт` и `Погрузка в ЖД транспорт`. Общие колонки `План` и `Итого` не заменяют норматив конкретного типа техники.
- Соответствия самосвалов: `Б75585` — 90 т, `Б75131` — 130 т, `Б75306` — 220 т, `Б75313` — 240 т. Категория 220 т добавляется в текущий справочник автотранспорта.
- Сопоставление обозначений PDF с типами сайта: `ЭКГ 10/8И` → `ЭКГ-10`, `ЭКГ-12А` → `ЭКГ-12`, `ЭКГ-12К` → `ЭКГ-12К`, `ЭКГ-15М` → `ЭКГ-15`, `ЭКГ 20КМ` → `ЭКГ-20`.
- Пустая ячейка PDF означает отсутствие настроенного норматива, а не нулевое время. Незаполненные сочетания нельзя создавать как `0`.
- `P&H 80` и `P&H 81` — разные экскаваторы/категории. На Главном карьере сейчас их нет, но модель данных в будущем не должна мешать различать их.
- Нормативы заполняются один раз при переносе на рабочий сервер, после чего остаются редактируемыми в настройках. Изменение справочника не пересчитывает сохранённые исторические отчёты. Пользователь уточнил, что реальные сменные отчёты в этом блоке пока не ведутся.

## 20. Итоговая картинка сменного отчёта для MAX

**Статус: согласовано и локально реализовано 10.10.2026; реальная отправка и рабочий сервер ещё не проверялись.**

- Отправляется только последняя сохранённая итоговая версия. Предварительные версии в MAX не отправляются.
- Процесс состоит из двух самостоятельных действий: `Данные заполнены` сохраняет неизменяемую итоговую версию и открывает предпросмотр; `Отправить в MAX` отправляет уже просмотренную версию.
- Формат — одно сообщение без текста, содержащее одну или несколько PNG-картинок. Макет рассчитан прежде всего на чтение с телефона.
- В отчёт входят только экскаваторы, по которым введены данные. Внутри экскаватора показатели сгруппированы; карточку одного ЭКГ нельзя переносить между двумя картинками.
- Показываются период, бригада, мастер, сводный план/факт/отклонение, все введённые производственные показатели, времена погрузки по видам транспорта, ожидания, выход негабарита для авто и полные причины отклонений.
- `Загрузка, %` хранится в БД и версиях для будущего использования, но в текущей картинке не показывается.
- Факт времени погрузки выше норматива и отрицательное отклонение выделяются красным. Незаполненные значения обозначаются прочерком на полупрозрачном красном фоне.
- Неполный итог не блокируется: перед сохранением мастер видит предупреждение и может вернуться к исправлению либо сознательно продолжить. После сохранения картинка остаётся доступна для просмотра до отдельной отправки.
- Адресат первого этапа — существующий бот и группа `Рапорт мастера`. Адресат задаётся закрытой серверной конфигурацией, а не текстом в исходниках.
- Сервер проверяет токен, идентичность бота, чат и членство бота перед отправкой. Повторная отправка одной версии блокируется. Неопределённый результат после сетевого сбоя не повторяется автоматически, чтобы не создать дубль.
- Ограничения официального MAX API соблюдаются: до 12 изображений в одном сообщении, не более 50 МБ и 7680×7680 каждое. Для текущего макета используется ширина 900 px и двухколоночные карточки, чтобы текст оставался читаемым при уменьшении до экрана телефона.
