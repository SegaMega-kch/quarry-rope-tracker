# MAX: справка по питанию экскаваторов

## Поведение

Одна кнопка **«Питание экскаваторов»** в одном сообщении бота, которое администратор группы закрепляет вручную. Нажатие обновляет это же сообщение без уведомления всей группе. Справка доступна только в согласованной группе «Рапорт мастера».

В ответе перечислены все действующие экскаваторы. Название выделено жирным, ниже указаны подключённые ЯКНО и известный горизонт экскаватора. Отметка **«(в сборку)»** означает реально подключённую рабочую сборку, независимо от ЯКНО. Свободные ЯКНО и незапитанные сборки рядом не считаются подключёнными. Неизвестный горизонт не выводится; отсутствие ЯКНО обозначается **«ЯКНО не подключено»**. Внизу стоит время снимка данных по Екатеринбургу.

Обычная переписка, личные диалоги и другие группы не обрабатываются. Бот не изменяет имущество или историю. Автоотчёты в 06:30 и 19:30 продолжают работать отдельным процессом с прежним состоянием отправки.

## Локальная проверка

`npm test` проверяет сбор данных, формат, защиту webhook, повторные события, одновременные запросы, перезапуск, недоступность источника/MAX и публикацию без дублей. Все MAX-вызовы в тестах подменены; данные создаются в отдельной временной БД. Дополнительно проверяется запрет записи в источник через отдельное SQLite-соединение `query_only`.

Для чтения локальной копии можно выполнить:

```sh
node node_modules/tsx/dist/cli.mjs scripts/run-max-reference.ts --config /absolute/private/reference-config.json --mode preview
```

Режим preview не читает токен, не открывает очередь и не обращается к MAX. Он выводит HTML-текст будущего сообщения. Реальное отображение кнопки и получение callback проверяются отдельно в MAX только после согласования публикации.

## Частная конфигурация

Отдельный файл `/root/raport-max/reference-config.json`, права 0600, родительский каталог 0700. Не добавлять поля в существующий config.json автоотчётов: его схема строгая. Пример с условными идентификаторами:

```json
{
  "sourceDatabase": "/root/quarry-rope-tracker/prisma/dev.db",
  "stateDatabase": "/root/raport-max/reference-state.db",
  "tokenFile": "/root/raport-max/token.txt",
  "webhookSecretFile": "/root/raport-max/reference-webhook-secret.txt",
  "webhookUrl": "https://rapmas.ru/api/max/reference",
  "botId": "123",
  "botUsername": "report_bot",
  "chatId": "-456",
  "chatTitle": "Рапорт мастера"
}
```

Использовать проверенные идентификаторы и существующий путь к токену. Секрет webhook новый, случайный, 32–256 символов A-Z/a-z/0-9/_/-, отдельный от токена. Ничего секретного не передавать в URL, командных аргументах или Git. `stateDatabase` не может совпадать с источником, конфигурацией или секретами, в том числе через symlink/hardlink. Инициализация эксклюзивная: существующие файлы не перезаписываются. Схема рабочей БД не меняется.

В окружении веб-процесса установить только путь `MAX_REFERENCE_CONFIG=/root/raport-max/reference-config.json`. Без него endpoint отвечает 404. Не отключать TLS. Существующий `NODE_EXTRA_CA_CERTS=/root/raport-max/russian-trusted-root.crt` нужен новому worker, как и рассылке.

## Порядок Включения

Все действия ниже выполняются оператором только после разрешения на GitHub и сервер. Команды подразумевают префикс `node node_modules/tsx/dist/cli.mjs scripts/run-max-reference.ts --config /root/raport-max/reference-config.json`.

1. Проверить локальные тесты/сборку, опубликовать согласованный код. На сервере сделать согласованную резервную копию рабочей БД и обоих состояний бота. Активная очередь рассылки после смены группы: `/root/raport-max/outbox-raport-master-20260927.db`; старый outbox.db не включать и не заменять новым состоянием справки. Не выполнять seed/reset или старую миграцию расписания.
2. Создать частную конфигурацию/секрет и выполнить `--mode init`. Начальное состояние выключено. `--mode preview` должен показать все действующие экскаваторы без сокращения списка.
3. Подключить env-путь к веб-процессу, проверить HTTPS endpoint: без секрета 401, для подписанного постороннего события 200. Настроить на прокси ограничение тела 64 КБ и таймаут входящего запроса. Код также ограничивает тело и время чтения, сравнивает секрет без утечки времени и не пишет содержимое запросов в лог.
4. Выполнить `--mode subscribe --send`. Разрешены только события `message_callback`; существующая другая подписка блокирует автоматическую замену и требует отдельного разбора. Ни `message_created`, ни чтение беседы не включаются.
5. Выполнить `--mode publish --send` ровно один раз. Сохранённый ID связывает кнопку с единственным сообщением. При неясном результате не повторять: см. восстановление ниже.
6. Выполнить `--mode activate`, затем запустить отдельный PM2-процесс из `scripts/max-reference.pm2.cjs`, задав абсолютные `MAX_REFERENCE_CONFIG` и `MAX_REFERENCE_CA_FILE` (путь к существующему российскому корневому сертификату). Не менять worker автоотчётов. Новый процесс считывает источник через отдельное соединение только для чтения. После live-проверки сохранить PM2-конфигурацию.
7. Пользователь закрепляет сообщение и нажимает кнопку. Проверить обновление времени в том же сообщении, правильные данные, повторные быстрые нажатия и отсутствие дополнительных сообщений. Проверить работу кнопки обычным участником. Без этого не объявлять функцию работающей.
8. Только после закрепления и успешного нажатия выполнить `--mode announce --send --confirm-pinned --confirm-tested`. Короткое объявление отправляется один раз независимо от расписания.

Документация MAX для GET /updates указывает, что групповые события требуют прав администратора; страница webhook не уточняет исключения для кнопок. Ручное закрепление не доказывает возможность получения callback без этих прав. Если callback не приходит, проверить подписку/секрет/прокси; необходимость роли согласовать с пользователем. Не назначать боту дополнительные права автоматически.

## Сбои И Восстановление

- Webhook только подтверждает надёжно сохранённый запрос. Дубликаты callback отсекаются на 48 часов; серия нажатий сворачивается в запрос актуальных данных. После перезапуска очередь остаётся на диске.
- Два worker не могут одновременно захватить обновление. Операции разнесены минимум на секунду после завершения предыдущей. Захват истекает через 120 секунд; перед сетевой операцией проверяется его актуальность. Новый снимок строится при каждой попытке.
- Если ответ на callback уже невозможен, следующая попытка редактирует сообщение по сохранённому ID. При сбое не отправляется новая справка. После пяти последовательных ошибок либо отказа доступа/удаления сообщения справка ставится на паузу. Автоотчёты не затрагиваются. Старая справка сохраняет прежнее время и не выдаётся за свежую.
- `--mode status` показывает enabled, pending, publication, announcement, failures и безопасный код ошибки. `--mode pause`, затем остановка `raport-max-reference` прекращают обработку; уже выполняющийся сетевой запрос может завершиться. Для восстановления причины устранить, выполнить `--mode activate`, запустить процесс. При длительной сетевой неопределённости проверить сообщение в группе перед возобновлением.
- Публикация/объявление заранее помечаются `review`. При обрыве соединения автоматической повторной отправки нет. Для найденного сообщения: `--mode resolve-sent --kind reference --message-id VERIFIED_ID` (или kind announcement). Проверяются автор, группа и назначение сообщения. Если отсутствие достоверно подтверждено, остановить worker, поставить справку на паузу и выполнить `--mode resolve-unsent --kind reference --confirm-not-delivered`, затем отдельно разрешённую публикацию. Не удалять/не пересоздавать state.db ради повтора.
- Если исходное сообщение удалено, не публиковать замену автоматически: сначала согласовать новую публикацию и закрепление. Режима сброса подтверждённого ID пока нет.
- При превышении лимита MAX 4000 символов список не обрезается и не разбивается на новые сообщения. Нужен согласованный новый формат до публикации/возобновления.
- Резервировать state.db согласованным SQLite-снимком либо после остановки worker и входящего webhook. Не восстанавливать старый снимок поверх рабочего состояния без сверки реально отправленных сообщений.

## Расширение

`referenceBuilders` содержит ровно один разрешённый обработчик. Следующую справку добавлять отдельным payload и явным сценарием, с проверкой группы, формата, объёма ответа и источника. Сейчас произвольных команд, личных ответов и изменения данных из MAX нет.
