# Распознавание фото: локальный пилот

Статус на 10.10.2026: диагностический экран в существующем разделе «Отчёт за смену». Это ещё не импорт данных: отчёт, статистика и архив исходных показателей не изменяются. Git и рабочий сервер не обновлялись.

## Выбор распознавателя

Локальный Tesseract проверен на двух предоставленных фотографиях. На хорошем фото он тоже теряет цифры и десятичные разделители: контрольное `10,57` прочитано как `1057`. Координаты таблицы не восстановлены. Его внутренний confidence не является оценкой правильности производственных данных. Эти результаты не доказывают непригодность других локальных движков; PaddleOCR пока не проверялся.

Подготовлен второй, явно включаемый режим — российский провайдер Yandex Vision OCR, модель `table`. Он подключён локально через отдельный сервисный аккаунт и проверен на двух исходных фотографиях. Хорошая фотография дала структуру таблицы и большинство значений, но одна пара строк объединилась; плохая фотография остаётся непригодной для автоматического импорта. Поэтому результат пока показывается только для проверки и ничего не заполняет автоматически. Необходимость разрешения компании на внешнюю обработку остаётся независимо от российского провайдера.

Официальные источники:

- [API распознавания](https://aistudio.yandex.ru/ru/docs/vision/ocr/api-ref/TextRecognition/recognize)
- [Модель table](https://aistudio.yandex.ru/ru/docs/vision/concepts/ocr/models)

## Настройка

Переменные задаются только на сервере, локально — в закрытом `.env.local`. Ключ нельзя помещать в Git, `NEXT_PUBLIC_*` или переписку.

```dotenv
PRODUCTION_OCR_PROVIDER=local
# Для явно согласованной внешней обработки:
# PRODUCTION_OCR_PROVIDER=yandex
# YANDEX_OCR_API_KEY=...
# YANDEX_OCR_FOLDER_ID=...
```

Распознавание доступно всем существующим учётным записям, которым разрешён раздел «Отчёт за смену» (shift, boss, admin). Отдельный белый список OCR больше не применяется. Роль кладовщика не допускается.

Локальная обработка использует поставляемые с зависимостями языковые модели, без их загрузки из интернета. Рабочему процессу не передаются API-ключи приложения. При ошибке переключения в облако нет. В режиме Yandex кнопка явно сообщает об отправке; запрос использует `x-data-logging-enabled: false`. Это не утверждение о сроках хранения/географии всей инфраструктуры провайдера — их нужно подтвердить отдельно до эксплуатации.

Блок фотографии полностью скрыт в обычной компьютерной версии. Он показывается только на телефонах и планшетах; сервер дополнительно проверяет мобильный заголовок интерфейса и User-Agent/Client Hints. Это защита от случайного использования с ПК, а не криптографический запрет для намеренно подменённого клиента. Разрешены камера и галерея. Пользователь должен снять крупно только раздел «Главный карьер».

Для локальной визуальной проверки при `RAPMAS_LOCAL_REVIEW=1` узкое окно до 800 px имитирует только видимость мобильного блока. Серверная проверка запроса при этом не ослабляется: отправка фото с компьютерным User-Agent по-прежнему отклоняется.

Серверный маршрут держит изображение в памяти, удаляет EXIF перед обработкой и не пишет фото/результат в архив или журналы приложения. После ответа исходная фотография отбрасывается; сохраняемого архива фото пока нет. Диагностический CLI ниже отдельно сохраняет локальные обработанные изображения в игнорируемый `outputs/production-ocr`; это не поведение сайта.

Ограничения: JPEG/PNG/WebP, до 10 МБ, 20 мегапикселей, минимум 1000×600; HEIC нужно преобразовать на телефоне. Один запрос на процесс одновременно, локальный таймаут 90 с, облачный 60 с. Для многопроцессного развёртывания нужны общая очередь и лимиты. Reverse proxy должен сохранять Host, разрешать тело запроса 11 МБ и ожидание не менее 100 с. Нагрузочный тест и промышленный лимит по пользователю пока не выполнены.

## Проверка

```powershell
npm test
npm run build
npx tsx scripts/check-production-ocr.ts <абсолютные пути к фото>
npx tsx scripts/verify-production-ocr.ts <абсолютные пути к фото>
```

Последняя команда предназначена только для локального стенда `127.0.0.1:3100`. Она проверяет авторизацию, запрет чужого Origin, обязательный мобильный контекст, формат запроса, реальные фотографии и неизменность истории отчёта. API Yandex дополнительно проверяется имитацией ответов/ошибок в unit-тестах.

Встроенный браузер запретил доступ к локальной вкладке. Визуальная и телефонная проверка не выполнены; HTTP-проверка не заменяет их.

Фактически выполнено: 181 тест без ошибок, `tsc --noEmit`, успешная сборка `npm run build` (предупреждение Next о нативном `<img>` для локального blob-предпросмотра). HTTP-проверка на двух оригинальных фото подтвердила ограничения доступа, видимость пилота только разрешённому ID, обработку фото и неизменность истории. Проверка исходников отдельным ревьюером завершена без открытых материальных замечаний, но не является визуальной приёмкой.

HTTP-сценарии повторно прошли на локальной собранной версии (`next start`, порт 3100). Установка зависимостей сообщила о 16 уязвимостях в общем дереве проекта; отдельный аудит и обновление существующих зависимостей не выполнялись. Перед эксплуатацией требуется отдельная проверка, без автоматического `audit fix` поверх текущих изменений. Служебная копия дизайн-контекста устарела относительно DESIGN.md; в этой задаче она не обновлялась.

## Следующий этап после проверки точности

Реализовать устойчивое сопоставление раздела «Главный карьер» с категориями, хранение структурированного исходного результата и экран исправлений. Только после этого — перенос подтверждённых полей в черновик. Десятичные минуты, разные категории руды/вскрыши, общий график бригад и защита ранее введённых полей остаются обязательными. Не подменять нечитаемое значение нулём.

### Проверка Yandex Cloud 10.10.2026

Личный Yandex Cloud настроен: отдельный сервисный аккаунт `rapmas-vision-ocr`, роль `ai.vision.user`, API-ключ с областью `yc.ai.foundationModels.execute`. Секрет хранится только в локальном `.env.local` и не выводился. Запросы отправлялись с `x-data-logging-enabled: false` после отдельного разрешения пользователя.

- Плохое фото: ответ `200`, таблица 12×21, только 6 непустых ячеек. Заголовок, дата и почти все показатели не прочитаны — фото непригодно для импорта.
- Хорошее фото: ответ `200`, таблица 25×25, 145 непустых ячеек. Прочитаны дата, смена, Главный карьер и многие показатели, включая `8,72`, `10,57`, `5,30`, `4,90`, `7,96`, `3,30`, итоговые `9,04` и `4,72`.
- Yandex объединил строки экскаваторов `46` и `58` (`46 58`) и их времена (`5,30 4,90`). Часть номеров строк не распознана. Поэтому автоматическое сопоставление и перенос остаются выключены.
- Две пустые служебные ячейки пересекали объединённый заголовок `№ экск`. Парсер теперь удаляет только пустой дубликат 1×1 внутри содержательной объединённой ячейки; конфликт двух непустых значений по-прежнему отклоняется.

Сырые ответы теста лежат только в игнорируемом каталоге `outputs/production-ocr`. Они не являются архивом сайта и не переносятся в Git.
