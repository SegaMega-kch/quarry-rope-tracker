# Развертывание на сервере

Эта памятка нужна для первого запуска проекта на удаленном сервере, например на Timeweb Cloud VPS.

## Что выбрать на сервере

Рекомендуемый вариант для первой рабочей версии:

- Ubuntu 24.04 LTS или Ubuntu 22.04 LTS
- 1-2 CPU
- 2 GB RAM
- 20-30 GB SSD
- ежедневный бэкап сервера или отдельный бэкап файла базы SQLite

## Что важно знать

Проект использует SQLite. Это значит, что рабочая база будет обычным файлом на сервере.

Файл базы не хранится в GitHub. GitHub хранит код приложения, а данные должны жить на сервере и регулярно копироваться в бэкап.

## Команды первого запуска

На сервере нужно установить Node.js LTS, затем выполнить:

```bash
git clone https://github.com/SegaMega-kch/quarry-rope-tracker.git
cd quarry-rope-tracker
cp .env.example .env
npm ci
npm run db:push
npm run db:seed
npm run build
npm run start
```

В файле `.env` для SQLite обычно достаточно:

```env
DATABASE_URL="file:./dev.db"
AUTH_SECRET="replace-me-with-long-random-text"
```

После `npm run db:seed` создаются начальные пользователи. Временный пароль: `123456`.

## Постоянный запуск

Для постоянной работы лучше запускать приложение через `pm2`:

```bash
npm install -g pm2
pm2 start npm --name quarry-rope-tracker -- run start
pm2 save
pm2 startup
```

## Обновление проекта

Обновление действующего сервера не должно заменять базу локальной копией.
Не запускать `db:seed`, `migrate reset`, `db push --force-reset`,
`--accept-data-loss` или `reconcile-crane-teeth.ts --apply`.
Не переносить локальный `.env.local`: на рабочем HTTPS-сайте cookie должны
оставаться Secure (`AUTH_COOKIE_SECURE=true` или настройка отсутствует).

Сначала проверить рабочую папку процесса PM2, фактический `DATABASE_URL`
(включая переопределение в окружении PM2), версию и локальные изменения Git.
Сохранить серверные изменения отдельно, не использовать принудительный сброс.
Обновление проводить в согласованное окно без записи работниками.

После публикации проверенного коммита можно получить только инструмент
резервного копирования, не переключая рабочую версию:

```bash
git fetch origin
mkdir -p backups
git show origin/main:scripts/deployment-data.cjs > backups/deployment-data.cjs
```

Следующие пути подходят только после подтверждения, что рабочая база именно
`prisma/dev.db`. При другой настройке подставить фактический путь.
Выполнять по этапам; при любой ошибке остановиться, не переходить дальше.

```bash
pm2 stop quarry-rope-tracker
backup="backups/deploy-$(date +%Y%m%d-%H%M%S)"
node backups/deployment-data.cjs backup prisma/dev.db "$backup"
```

Продолжать только после `BACKUP VERIFIED`. Каталог закрыт для других
пользователей; внутри согласованная копия SQLite (включая данные из WAL)
и контрольные суммы всех значений всех существующих таблиц. Сам инструмент
не изменяет исходные данные. Сохранить также настройки и прежний коммит:

```bash
cp -p .env "$backup/environment.env"
git rev-parse HEAD > "$backup/code-commit.txt"
git merge --ff-only origin/main
npm ci
npm run db:push
npm run build
node scripts/deployment-data.cjs verify prisma/dev.db "$backup"
```

Перед переключением убедиться, что `origin/main` соответствует проверенному
коммиту. При изменениях файлов или несовместимой схеме не продолжать вслепую.
Лучше предварительно применить новую схему к отдельной копии резервной базы
и проверить ее тем же инструментом. В каталоге копии нужен собственный
снимок `backup`, так как проверка привязана к исходному пути базы.

Только после `DATA VERIFIED` запустить приложение:

```bash
pm2 restart quarry-rope-tracker --update-env
pm2 save
pm2 status
pm2 logs quarry-rope-tracker --lines 30 --nostream
```

Проверить вход, семь вкладок, фактические остатки и места в браузере.
Сверку неизменности выполнять до открытия доступа на запись: рабочие
действия сотрудников после запуска закономерно меняют базу.

При ошибке сверки приложение оставить остановленным. Сначала сохранить
неудачное состояние для разбора; восстановление возможно только совместно
из сохраненного коммита и его базы, при остановленных процессах. Не удалять
резервные копии и не накатывать старую базу поверх новых действий работников.

## Бэкап данных

Не копировать только основной файл работающей SQLite: последние записи
могут находиться в WAL. Для согласованной копии использовать инструмент:

```bash
mkdir -p backups
node scripts/deployment-data.cjs backup prisma/dev.db "backups/manual-$(date +%F-%H-%M-%S)"
```

Для строгой сверки остановить запись на время выполнения; если данные
изменились между созданием копии и проверкой, инструмент завершится ошибкой.

Лучше настроить автоматический ежедневный бэкап через панель Timeweb или отдельную команду `cron`.
